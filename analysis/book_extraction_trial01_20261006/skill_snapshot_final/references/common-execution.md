# 共用执行流程

## 本机入口与初态

先查看项目 `PROJECT_HANDOVER.md` 的最新带时间条目、`MACHINE_INITIALIZATION_RUNBOOK.md`，并核对现有代码。文件中的“当前”可能是历史快照，不能直接相信旧 PID 或设备号。查连接问题时检索既有 MD 的 CAN、SDK motor fault、heartbeat、camera、settle 条目，按具体症状处理，不把接口 UP 当作电机反馈正常。

本机历史映射为物理左臂 `can0`（全局画面右侧）、物理右臂 `can1`（全局画面左侧）；三相机键为 `external`、`gemini`、`gemini_right`。每次用当前身份、新图与反馈核实。两臂基坐标独立，画面左右不等于基坐标正负；不得用上一轮固定增量猜方向。

用户通常授权一轮完整操作及必要局部修正。已确认摆放/清场且画面未变化时直接推进，不反复确认。断电插座状态、目标变体等必要信息缺失时才问。人工调整、新人员侵入或状态矛盾出现后重新核实有关条件。

区分两种入口：

- **冷启动**：核验 ready、disabled、stationary、无 owner、反馈新鲜、无 SDK 错误、有效关节及夹爪范围、三路图像设备一致且序号递增，再按现有标准入口建立保持。SDK 重连可能有初始化动作，不是纯只读检查；若本轮需要重连，录像与清场必须先满足。
- **健康保持续行**：核验原宿主有效、owner 正确、两臂状态/夹爪目标与日志一致；复用宿主或经已有检查交接，不能启动竞争控制器或重复使能。故障锁存宿主不属于健康续行。

保存本轮初始状态及不可随预算更新改写的 `return_reference.json`。若连续健康宿主明确继承上轮原参考，保存本轮初态并注明继承来源，不把中途姿态当“最初位置”。取花与预置持花、不同容器等初态也写入冻结 prompt。

现有入口包括 `tools/single_policy_review.py`、`tools/held_policy_review.py`；调用前查当前源码/帮助，不从历史日志复制启动参数。由单臂转为双臂观察必须通过适用的受检交接，一次一侧接收目标，另一侧保持；不能在单臂宿主之外另起右臂控制器。

## 三路 MP4

用户持续偏好：每次执行都录全局、左腕、右腕，MP4 格式。具体行为见项目 `THREE_CAMERA_RECORDING.md` 及 `tools/record_three_cameras.py`。

为本轮新建唯一目录，使用真实目录名替换示例中的 `<trial>` 后执行：

```bash
.venv-policy/bin/python -u tools/record_three_cameras.py --output 'analysis/<trial>/recording' --format mp4
```

在项目根目录运行，保持录像进程可追踪。脚本默认格式仍可能为 AVI，必须显式 `--format mp4`。现有服务通过 HTTP 提供相机图像，不另开 `/dev/video*` 争抢设备。独占锁用于避免重复录像；若已有录制，先识别所属任务与目录，不盲杀其他终端。

首次会改变硬件的操作前，确认 manifest 为 `recording`、进程存在、心跳新鲜、三路设备不同、各路 `fresh_frames` 连续增长。控制侧也必须取得新鲜观察；录像截图不能替代。运行中继续检查，含使能/交接和每次任务运动前。录像中断时暂停新运动并保留健康保持宿主，先恢复记录，写清缺口；不能用录像恢复替代运动故障恢复。

按现有默认 10 fps、60 秒分段记录，除非用户指定其他格式/频率。缺采样和重复源帧保留标注与计数；共同软件采样时基不是相机曝光硬同步，不称“全程零缺帧”。

录像首帧超时、随后单帧检查正常时，先检查相机闲置停流：本机CameraStream闲置4秒会停流，冷启动可能超过录像客户端原1秒请求期限。可先只读预热三路，验证新帧及身份，并在相机仍活跃时立即启动录像；不放宽录制或运动监督超时。初始失败manifest保留，新目录重启，运动仍以三路正常录制为前提。

## 看图与动作循环

用户要求自主探索，尽量不要求接管或回答几何问题。把全局、左腕、右腕作为互补信息源：全局检查整臂和场景，腕部核对夹持与接触；某一路遮挡时先用其他两路，必要时保持工作臂、让空的观察臂在已检查通道内改变位置取得视差。旋转相机只改变构图，平移才增加观察基线；始终检查观察臂全部连杆、夹指和线缆。

带着具体不确定性选观察位，比较动作前后物体、支撑物及静态背景的响应，再决定下一步。不要把二维重叠写成穿入，不把关节到位写成物体成功。可观察的问题由 agent 自己核验；三路并不保证能消除所有遮挡。证据仍不足时保留未完成结果和具体阻碍，不连续试探同一接触，也不要求用户代答是否成功。只对无法由传感器获知、确实影响执行的目标/权限或新人员进入等条件询问；沿用当前已有效的授权与清场信息。

控制期间只记必要检查点，结束后集中写公开对话和完整 MD。先离线规划，再获取并审阅新图、及时下发，减少观察过期与重复读取。统计命令处理、抓图和命令间等待，命令间等待不能全部称为模型推理。

1. 规划前读当前状态与命令残差，审阅全局和有效第二视角；校准未经验证时只据可见方向、相对位置、间隙决策，不报告毫米级实物定位精度。
   取图/显示图像与依赖该图像的运动下发必须分开调用，让模型实际审阅新图后再决定。不能在同一个编排调用里先 `view_image` 再自动下发运动；程序顺序执行不等于已经完成视觉审阅。旋螺栓第1轮曾因此漏过新进入的人手，相关失败保留在该轮记录中。
2. 接近时先对齐高度和前后距离，再逐步闭爪。不能用“闭合更多/更有力”弥补夹指根本没包围物体；开度是位置，不能冒充夹持力。
3. 生成有界目标，保留当前速度、关节余量、轨迹、跟踪、到位和预算检查。数值规划不包含已验证的完整碰撞检测或接触力控；另看整臂、末端、相机、线缆、负载和障碍。
4. 在现有观察有效期内下发；若观察过期，刷新、复核、重算，不放宽期限。一次仅运动一臂，另一臂保持。右臂若要换观察位，先停止左臂新动作。
5. 每步等到反馈检查通过再看新图，核对物体真实响应。阻挡、容器随动、滑移、弯曲、遮挡造成不可判定时停止推进；在可确认支撑和路径条件下才执行回撤/重夹。
6. 同一抓取点连续两次试提失败时，停止重复闭爪或提升，重新检查深度、夹持部位、支撑和视角；只有取得新的可行抓取依据才局部重试。没有新证据或有不明接触时保持暂停并说明阻碍。局部重试属于原试次，不自动增加轮次。

历史已用限制为平移 0.01 m/s、旋转 0.05 rad/s、关节 9°/s、控制器速度 0.3，原 2°关节边界余量外另加 3.5°指令规划余量，以及 30 秒观察有效期。它们是核对既有配置的依据，不能为套用模板覆盖当前配置或降低更严格限制。实际宿主与代码不一致时先查明。

只有健康静止、无不明接触且原续段条件通过时，才能使用已有 renew 重锚当前工作臂的预算。续段后重新取图与状态、重新规划，保留原回位参考。不顺带重锚非工作臂；不把 renew 当作清除故障或无限重复失败的入口。

## 故障与收尾

区分动作前拒绝（例如观察过期、规划余量不足）与运行故障。相机故障锁存、心跳超时、到位失败、CAN 无回包不是同一原因。不能因为三路录像正常就否定控制监督故障，不能将未查明的超时归因于 GPT 和硬件“冲突”。

已有相机保持恢复只适用于代码规定的严格静止条件；若需使用，先检查当前实现、日志与离线验证，保留旧故障，不改日志骗取交接。未知 CAN/供电问题按初始化手册处理，不循环 SDK 重连，更不关闭保护强行运动。

2026-10-05新增可选的关节到位故障保持，见项目 [FAULT_POWERED_HOLD_20261005.md](/home/tuojing/arx_r5_control/FAULT_POWERED_HOLD_20261005.md)。`--retain-settle-fault-hold` 默认关闭，只用于普通单臂轮流操作、严格相机监督的双臂宿主；进入后原故障不清除、任务队列永久隔离，只维持健康静止保持。此项仅离线验证，不能视为防坠装置，也不能用于在已知失能落桌、承托尚未解决的情况下直接重试。

放置后逐步松爪、空爪撤离，以至少两次相隔数秒的新观察核验独立支撑与容器稳定。随后沿可见有界路径空爪回到本轮保存参考；分别核验两臂实测关节、指令关节、静止状态，沿用原 2.5°容差。参考因边界余量不能完全重合时只接受原容差内的可执行目标并如实注明，不篡改参考或放宽容差。未受控回位就明确记未完成。

正常收尾创建本轮录像目录的 `STOP`，等待进程退出和 manifest=`completed`，验证全部 MP4 的首末帧与片段/帧数，并注明检查范围（首末帧可解码不等于逐帧检查）。用户若要求提前停止录制，按要求停止并记录缺口，不能声称此后全程有录像。整理 MD 和状态后报告结果、回位、录像位置。

停止录像不等于停止控制。不得为了结束会话、清理终端或完成文档关闭健康保持宿主；持物/伸展状态尤其不能以失能收尾。任何历史“故障后折叠”与 SDK 初始化都不能算受控回位。
